### User Story 1 - Configure deterministic parameter sweeps (Priority: P1)

Strategy owners need to describe sweep-ready parameters (single value, explicit list, or numerical range) so the backend can expand them into deterministic combinations without manual scripting.

**Why this priority**: Without structured sweep input, users cannot generate comparable runs across multiple parameter sets, undermining the feature’s core value.

**Independent Test**: Submit a backtest request containing mixed parameter definitions and confirm the system produces a deterministic combination set with one canonical run per combo (single ticker and multi-ticker payloads both remain supported).

**Acceptance Scenarios**:

1. **Given** a payload with single values, lists, and range definitions, **When** the sweep processor validates the request, **Then** it normalizes every parameter into a deterministic ordered list and rejects malformed ranges with a user-facing error.
2. **Given** a sweep request inside the configured combination cap, **When** the backend expands the set, **Then** it produces run configurations whose hashes are stable across repeated submissions with identical input.
4. **Given** any sweep submission, **When** payload validation, normalization, orchestrator gating, and manifest persistence run, **Then** each checkpoint emits a data-quality verdict and telemetry slice so reviewers can confirm clean data propagation end-to-end.

### Edge Cases

- What happens when range definitions produce floating-point step increments that do not land exactly on the stop value? The system should normalize using deterministic rounding and discard out-of-bound values.
- How does the system handle duplicate parameter combinations generated by overlapping lists and ranges? Duplicate combos must be deduplicated before execution while preserving deterministic order.
- What occurs if a sweep includes parameter ranges that expand to zero combinations after normalization? The request should fail closed with a descriptive validation error before any runs start.
- How are retries handled when an individual child run fails trust gates or runtime validation? The parent manifest should record failure status and allow targeted re-execution of only the affected combinations.
- What happens when a multi-ticker submission produces zero combinations for one ticker but valid combinations for others? The specification should define whether the partial sweep proceeds, how manifests reflect the partial success, and how telemetry flags the condition.
- How are per-ticker cap exceedances handled when one ticker breaches limits and others remain within bounds? Requirements must state whether compliant tickers proceed and how warnings/waivers are recorded, including manifest notes (`cap_status=hit`, `reviewer_required=true`) for the offending ticker and `data_quality_status` inheritance for untouched tickers.
- What responses are required when mid-sweep data anomalies (precision drift, duplicate combos reintroduced after hashing, or data-quality regression during execution) are detected? Telemetry must flag the offending ticker/combination, pause scheduling until reviewer acknowledgement, and persist the anomaly context in the manifest.
- How should the system respond to incomplete or malformed financial inputs (missing price history, null indicators, out-of-domain parameter values) prior to expansion? Trust gates must fail validation with actionable error codes and record the failure in telemetry and manifests.

- **FR-003**: System MUST enforce the global combination cap derived from the existing optimization limit configuration, aborting requests that exceed the limit with an `OPTIMIZATION_SWEEP_LIMIT_HIT` warning and without scheduling any runs.
- **FR-004**: System MUST execute sweep combinations sequentially (or via a deterministic work queue) to preserve repeatable ordering and trust-gate evidence.
- **FR-005**: System MUST generate a parent sweep manifest that records child run hashes, originating parameter values, aggregate telemetry, and storage impact, and persist it using the versioned governance contract for artifacts.

### Testing Remediation Alignment

To restore a truthful full-suite green state while delivering this feature, the team will:

1. Update `/runs` contract tests to respect the asynchronous `202 Accepted` response and verify sweep-specific fields after polling the run detail endpoint.
2. Right-size pytest coverage gates by constraining enforced modules and introducing diff-aware checks so legacy debt stays visible without blocking Param Sweep progress.
3. Document and standardize lightweight validation fixtures, reserving the full Masters pipeline for a dedicated smoke job tracked in governance artifacts.

Completion of this remediation stream is a release prerequisite for the feature branch.
### Key Entities *(include if feature involves data)*
- **ParameterDefinition**: Represents a strategy parameter supplied as a single value, explicit list, or range, including metadata required for deterministic normalization.

- **Clean Data Definition**: Clean or financially logical data must pass null checks, respect strategy-defined value ranges, apply deterministic rounding (≤6 decimal places) to numeric parameters, and remain deduplicated after normalization.

### Clean Data Propagation Flow

1. **Ingestion & Baseline Validation**: Existing Brain data-cleansing services deliver curated price history and indicators to the sweep request builder; payloads entering the sweep API must reference these curated datasets, explicitly confirming reliance on the upstream validation catalog.
2. **Payload Trust Gate** *(Checkpoint: `payload_validation`)*: The API schema validates strategy, parameters, and per-ticker inputs. It records sanitized parameter snapshots (`sanitized_parameters`) and a `data_quality_status` verdict in the parent manifest before expansion begins.
3. **Normalization Trust Gate** *(Checkpoint: `normalization`)*: `ParameterDefinition` normalization deduplicates and rounds values using the declared precision. The manifest stores both the normalized list and any anomalies (e.g., discarded floats), while telemetry emits `data_quality_status=pass|fail` to distinguish data hygiene issues from cap triggers.
4. **Orchestrator Trust Gate** *(Checkpoint: `orchestrator`)*: Combination expansion runs per ticker, enforcing `AF_OPTIMIZATION_MAX_COMBINATIONS` independently for every ticker. Guardrail failures surface `cap_status=hit` while preserving `data_quality_status`, enabling reviewers to see whether the rejection arose from data or cap concerns.
5. **Manifest Persistence Trust Gate** *(Checkpoint: `manifest`)*: Completed sweeps write parent and per-ticker manifests capturing child run hashes, derived metrics, and trust-gate notes. The manifest stores the final `data_quality_status`, per-ticker storage footprint, and variance metrics linking back to baseline runs.

Telemetry for each checkpoint includes latency spans so auditors can confirm that additional cleansing steps remain inside the SC-002 performance envelope.

### Multi-Ticker Semantics & Evidence

- **Submission Format**: Sweep payloads list tickers under `payload.tickers` with each ticker referencing the shared `strategy.parameters`. Each ticker is processed independently; no cross-ticker cartesian expansion occurs, and existing single-ticker submissions remain unchanged.
- **Per-Ticker Expansion**: The sweep orchestrator materializes one `RunConfig` set per ticker by reusing `ParameterDefinition`. Combination IDs include the ticker slug (`<ticker>::<hash>`) to guarantee uniqueness without cross-contamination.
- **Per-Ticker Guardrails**: Combination caps apply per ticker. If a specific ticker exceeds the configured cap, its section is rejected with `cap_status=hit` while compliant tickers may proceed when waivers allow, and manifests must record the partial outcome plus reviewer notes.
- **Manifest Layout**: Parent manifest entries reference `zz_artifacts/sweeps/<sweep_id>/<ticker>/manifest.json`, and telemetry labels include `ticker=<symbol>` to align dashboards and retention evidence. Naming guidance ensures reviewers can reconcile per-ticker data quickly.
- **Success Evidence**: SC-005 requires parity between multi- and single-ticker runs. Acceptance testing captures variance deltas (≤0.1%) and ensures multi-ticker manifests embed comparisons to baseline single-ticker executions for each KPI (PNL, drawdown, trade count).

## Success Criteria *(mandatory)*
### Measurable Outcomes
- **SC-001**: 100% of sweep requests reproduce identical combination ordering and child run hashes when submitted with identical inputs on separate days.
- **SC-002**: 95% of sweeps completing within the configured combination cap finish execution and parent manifest assembly within 10% overhead compared to running the same combinations individually.
- **SC-003**: All sweeps exceeding the combination cap are rejected in under 2 seconds with an actionable warning recorded in audit logs.
- **SC-004**: Governance dashboards receive sweep telemetry (counts, durations, limit rejections) within one reporting interval (≤60 seconds) of sweep completion.
- **SC-005**: Multi-ticker submissions produce per-ticker results identical to executing each ticker separately, and manifest/telemetry evidence confirms the absence of cross-ticker interference.
- **SC-006**: Clean-data KPIs (PNL, drawdown, trade count) differ by ≤0.1% between sweep outputs and baseline single-run executions; deviations trigger a data-quality alert and checkpoint review.

## Assumptions
- Sweep execution foundations are backend-only in this phase; Mind UI integration will consume the new APIs in a future feature.
- Existing trust gates, retention policies, and artifact storage mechanisms can be extended without re-architecting underlying infrastructure.
- Numeric range inputs follow inclusive start and exclusive stop semantics unless the step lands exactly on the stop value.
- Single-ticker backtests and existing automation workflows remain unchanged; multi-ticker support augments rather than replaces the current request format.
- Existing data-validation and reconciliation services within alphaforge-brain remain authoritative for input cleansing, and sweeps must leverage their outputs or surface waivers before execution.

## Dependencies
- Versioned persistence contract updates that capture sweep metadata.
- Governance telemetry pipelines already deployed for existing deterministic runs.
- The existing optimization combination limit configuration remains the authoritative guardrail for combination limits.
